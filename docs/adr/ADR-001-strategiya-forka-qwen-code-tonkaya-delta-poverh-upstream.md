# ADR-001. Стратегия форка Qwen Code: тонкая дельта поверх upstream

- Date: 2026-09-26
- Status: Proposed (решение человека на гейте A3 — обязательное, маршрут Critical)

> **Rev 2 (2026-09-26, ратификация по итогам прогона `hr-20260926-205640-02`).** Объявленный состав дельты («ровно два файла») оказался недостаточным по факту базы — и это признано архитектором, а не «исправлено молча»:
>
> 1. **`packages/core/src/permissions/autoMode.ts` — ратифицирован как третий файл дельты.** Правка ровно одна: аддитивное расширение union `AutoModeDecision.stage` значением `'jev'` (без логики). Причина: union объявлен в базе дважды (`ClassifierResult` и `AutoModeDecision`), и без второго объявления `tsc` не проходит критерий приёмки §8.2 спеки. Типобезопасность важнее косметики списка файлов.
> 2. **`packages/cli/src/config/config.ts` и `settingsSchema` — разрешены как проводка настроек** (четвёртый и пятый файлы). Причина: без них `settings.jev` из `settings.json` не доходит до ядра, и включение стадии возможно только программно — то есть фича неработоспособна для пользователя. Правки — аддитивные (ключ в схеме + проброс в `ConfigParameters`), без логики.
> 3. **Правило для всех upstream-файлов дельты (уточнение, проверяется ревью):** в них допускаются только (а) врезка вызова стадии, (б) аддитивные типы/unions, (в) проводка настроек. Любая **логика** (условия, ветвления, политика) обязана жить в `packages/core/src/jev/**`. Каждая правка upstream-файла помечена ссылкой на ADR.
> 4. Состав дельты теперь перечисляется в `CONSTRAINTS.yaml` (правило `upstream_delta_scope`) — единый источник правды, а не проза в ADR: расширение списка невозможно без явного изменения правила и ревью.
> 5. Имена файлов пакета — kebab-case по требованию eslint репозитория (`decision-log.ts`, `backends/systemone.ts`); спека приведена в соответствие.

## Context

- Форк существует и используется: `<workspace>`, `origin = github.com/romannekrasovaillm/qwen-code`, `upstream = QwenLM/qwen-code`. На момент решения HEAD форка — merge upstream от 2026-03-26; upstream ушёл вперёд (в разведке — 0.24.6 против установленного 0.24.4), ветки/PR идут непрерывно.
- Целевая точка врезки Jev — **ядро безопасности**: `packages/core/src/permissions/` (AUTO-режим разрешений, `classifier.ts`, `autoMode.ts`). Это самый конфликтогенный участок upstream: там идут регулярные правки (слои L5.x, dangerousRules, denialTracking) — см. `docs/developers`-раздел и историю PR.
- Задача проекта (решение владельца, A3, 2026-09-26): Jev становится быстрым гейтом разрешений в ядре — **не** внешним хуком/MCP-мостом.
- Форк исторически накапливал нецелевой мусор в рабочем дереве (`games/snake`, `run-deepseek-agent.sh`, незакоммиченные скрипты) — рабочее дерево владельца грязное, работа в нём без изоляции создаёт риск потери чужих правок.

## Decision

**Тонкая дельта.** Jev-гейт вносится как изолированный модуль ядра с одной точкой врезки, выключенный по умолчанию:

1. Новый код — только в новых путях: `packages/core/src/jev/` (клиент, адаптеры бэкенда, сборщик `state`, гейт-логика, журнал решений).
2. Правки существующих файлов — минимальные и локализованные: `permissions/classifier.ts` (врезка Jev-стадии перед stage-1 LLM) и `config/config.ts` (блок настроек `jev`). Число изменённых upstream-строк — под контролем fitness-функции (потолок живёт в `CONSTRAINTS.yaml`, не в прозе).
3. Фича-флаг **выключен по умолчанию** (`settings.jev.enabled = false`): поведение продукта без явной настройки остаётся побитово прежним.
4. Работа — в git worktree (`arch/jev-stage1`), основное дерево форка не трогается. Синхронизация: регулярный `merge upstream/main`; конфликты допустимы только в двух объявленных точках врезки.
5. Продуктовая идентичность: форк остаётся сборкой Qwen Code (лицензия Apache-2.0, `LICENSE` и уведомления upstream сохраняются); в `README` форка добавляется раздел о дельте и о внешнем вендоре решений.

## Alternatives Considered

| Вариант                                                      | Плюсы                                                                                                             | Минусы                                                                                                                                            |
| ------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Тонкая дельта (выбрано)**                                  | Дешёвый мерж upstream; риск изолирован в одном модуле; откат = выключить флаг; поведение по умолчанию не меняется | Ограничение «в одной точке врезки» сковывает дизайн; upstream может отрефакторить `classifier.ts` и врезка «поедет» — нужен страж на форму врезки |
| Hard fork: свободная правка ядра под Jev                     | Максимум свободы (переписать AUTO-контур целиком, добавить журналы и метрики везде)                               | Мерж upstream становится работой с конфликтами в глубине ядра; поддержка растёт линейно с активностью upstream; откат дорогой                     |
| Без форка: Jev через `PreToolUse`-хук / MCP-мост (Jevbridge) | Ноль правок ядра, быстрый пилот, обновляемость                                                                    | Хук возвращает `allow                                                                                                                             | deny | ask` (`hooks/types.ts:793`), но **не может заменить решение fast-стадии классификатора** и не даёт встроенных метрик/каскада — целевой сценарий владельца не достигается. Остаётся быстрым путём для пилота (см. ADR-002, «shadow» вне ядра) |
| PR в upstream QwenLM                                         | Не поддержка форка вовсе                                                                                          | Внешняя зависимость от TypeSafe API в security-пути upstream не пройдёт ревью; для задач владельца (свой периметр, свой вендор) — не вариант      |

## Consequences

### Positive

- Дельта смотрится одним диффом: один новый пакет + две точки касания; ревью — вместе с кодом в PR ветки.
- Владелец форка может обновлять upstream, не разбирая чужую переписку AUTO-контура.
- Откат — конфиг, а не revert ядра: `settings.jev.enabled = false` возвращает исходное поведение.

### Negative

- Дисциплина «одна точка врезки» ограничивает: любые будущие Jev-места (guardrails на входе, роутинг моделей) потребуют собственного ADR и своих точек — иначе дельта расползётся.
- Upstream-рефакторинг `classifier.ts`/`autoMode.ts` объективно сломает врезку. Принимаем: фиксируем **функциональный контракт** (см. ADR-002), а не номера строк, и проверяем врезку fitness-функцией на форму (наличие вызова Jev-стадии + сохранение каскада).
- Форк навсегда несёт обязательство синхронизации; без периодического `merge upstream/main` дельта деградирует в hard fork де-факто.

## Reversibility

**reversible.** Обратная операция: `settings.jev.enabled = false` (мгновенно, без кода) либо drop ветки `arch/jev-stage1` (git-операция; основное дерево и upstream-история не тронуты). Необратимой цены нет, потому что правки ядра локализованы и объявлены.
