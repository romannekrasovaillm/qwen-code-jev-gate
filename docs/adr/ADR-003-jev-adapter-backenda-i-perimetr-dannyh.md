# ADR-003. Адаптер бэкенда Jev и периметр данных: минимизированный state, ключ только из окружения

- Date: 2026-09-26
- Status: **Accepted с поправкой Rev 2** (см. ниже; часть «выбор носителя решения» переопределена ADR-004)

> **Rev 2 (2026-09-26, решение владельца A3).** Вендорский TypeSafe API выведен из целевого контура: носитель решения — локальный Jev-совместимый сервер, внешние вызовы из Jev-стадии запрещены (ADR-004, AD-10 спайна). Что остаётся в силе из этого ADR: (1) единый интерфейс `JevBackend` и разделение реализации/конфигурации; (2) закрытый периметр `state` — минимизированный набор полей без транскрипта и содержимого файлов; (3) детерминированная редакция секретов; (4) запрет секретов в артефактах; (5) методика пилота и правило «пороги только после reliability curve». Что заменено: `typesafe-api` не является боевым бэкендом; вместо него — локальный носитель (см. ADR-004 §3); ключ `TYPESAFE_API_KEY` остаётся допустимым только для разового сравнения вне контура, но в целевом решении не используется.

## Context

- Доступ к Jev — только по внешнему API: `POST https://api.typesafe.ai/v1/systemone`, `Authorization: Bearer $TYPESAFE_API_KEY`, модель `jev-latest`; SDK `typesafe-sdk` (Python ≥3.10). Веса закрыты, early access.
- **На стенде ключа нет** (`env | grep -i typesafe` — пусто), а пилот по методике `jev-pilot-harness` обязан стартовать без блокировки: сухой режим + добавление кандидата `jev` позже **без переписывания протокола**.
- Решение владельца (A3): точка врезки — ядро, в путях разрешений агента; значит `state` собирается из аргументов вызова инструмента и метаданных сессии. Это потенциально **содержимое рабочего кода владельца**, уходящее третьей стороне (вендор в early access) — это security/privacy boundary, а не деталь реализации.
- Слабые места, влияющие на дизайн: Jev хуже отвечает на шумном большом `state`; восприимчив к состязательному контенту внутри `state`; при смене вендором модели/цены наш контур не должен ломаться.

## Decision

1. **Единый интерфейс бэкенда.** `JevBackend.decide(state, questions, opts): Promise<JevDecision>` в `packages/core/src/jev/backends/`. Реализации:
   - `typesafe-api` — боевой путь (HTTP/SDK, `jev-latest`);
   - `system-one-adapter` — LLM, отвечающая на те же типизированные вопросы (`system-one-adapter[openai|anthropic|gemini]`): честный конкурент в пилоте и запасной путь, **не** молчаливая подмена боевого бэкенда;
   - `dry-run` — локальный детерминированный скорер: разработка, тесты, дым-тест контура. Является **не сигналом безопасности**: его исходы в решениях гейта запрещены (может использоваться только при `mode='shadow'`).
2. **Выбор бэкенда — конфигом** (`settings.jev.backend`), без автоматического переключения между вендором и adapter-LLM в рантайме: подмена бэкенда меняет семантику решения и должна быть видна в конфиге и журнале.
3. **Секреты.** `TYPESAFE_API_KEY` — только из окружения; в конфиг, журнал, отчёты, телеметрию и тестовые фикстуры не попадает. Тесты используют фейковый транспорт, не реальный ключ. Утечка ключа в артефакты — дефект уровня блокера.
4. **Периметр данных (что уходит вендору).** В `state` допускаются: имя инструмента, канонизированная команда/аргументы после редакции, класс пути (workspace/external), cwd-класс, детерминированные признаки, — и **ничего сверх этого**. Запрещено передавать: содержимое файлов и результатов инструментов, транскрипт диалога, переменные окружения, значения, похожие на секреты (ключи, токены, пароли, приватные ключи), персональные данные третьих лиц. Редакция — **детерминированный, покрытый тестами фильтр в коде**, а не просьба к модели; фильтр выполняется до формирования запроса.
5. **Расширение периметра — только отдельным решением.** Передача транскрипта/содержимого (как это делает текущий LLM-классификатор: до 40 сообщений, 40 000 символов истории) допускается лишь новым ADR с решением владельца и явной оценкой риска. До этого периметр закрыт.
6. **Пилот до прода (методика `jev-pilot-harness`).** Артефакты в `pilot/`: замороженный спек вопросов + его хеш; сборщик `state` — одна функция для всех кандидатов; матрица кандидатов (`jev`, `llm-adapter`, `prompt-monolith`, `baseline-ml`, `heuristic` — только дым-тест); метрики: agreement с эталоном + confusion, p50/p95/p99 латентности, цена за 1K решений, schema-valid rate, reliability curve/ECE, доля низкоуверенных; критерии `accept / cascade / reject`.
7. **Пороги `confidence` включаются позже.** До монотонной reliability curve на своём корпусе пороги не используются для расширения автоматизации (это согласовано с ADR-002: v1 — escalate-only). Изменение режима `block-only → enforce` требует: (а) кривой калибровки, (б) порогов по классам риска из асимметрии цены ошибки, (в) решения владельца.
8. **Стоимость и бюджет.** У Jev-стадии есть денежный/токенный предохранитель (суточный потолок + счётчик в журнале), потому что вызов происходит на каждом разрешаемом действии AUTO-режима. Заявленные вендором цифры (цена/латентность) в проектирование не закладываются как факт — только как гипотеза, проверяемая пилотом.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Адаптер с тремя бэкендами (выбрано)** | Пилот стартует без ключа; честный baseline тем же спеком вопросов; вендор-лок ослаблен; тесты идут без сети | Дополнительный слой абстракции; adapter-LLM — не тот же объект измерения, что Jev (меряется отдельным кандидатом, а не подменяет его) |
| Только нативный Jev API | Проще всего, меньше кода | Блокировка всего проекта на одном ключе внешнего вендора (early access); невозможен честный baseline тем же спеком |
| Только `system-one-adapter` (LLM как System One) | Работает на наших ключах, воспроизводимо | Мы не проверяем предмет (Jev) вообще; теряется смысл проекта |
| MCP-мост Jevbridge как прод-путь | Изоляция, готовый мост, не нужны SDK | Внешний процесс в горячем пути разрешений — лишняя точка отказа и латентности; остаётся допустимым **кандидатом пилота**, не боевым путём |
| Передавать транскрипт, как делает LLM-классификатор | Больше контекста → возможно, точнее | Утечка содержимого рабочего кода третьей стороне; нарушает минимизацию и повышает состязательную поверхность |

## Consequences

### Positive

- Проект не заблокирован отсутствием ключа: пилот, тесты и walking skeleton собираются сразу, `jev` добавляется включением бэкенда.
- Вендор-риск управляем: смена вендора/цены/недоступность → конфиг и деградация, а не переписывание ядра.
- Периметр данных зафиксирован явно и проверяем механически (фильтр + тесты + фитнес-правило «в сборщике `state` нет запрещённых полей»).
- Появляется измеримая база решения: свои числа вместо вендорских.

### Negative

- **Минимизированный `state` может снизить точность против полного контекста** — это осознанный размен в пользу периметра; проверяется в пилоте (вариант «расширенный `state`» меряется отдельным кандидатом на синтетике/обезличенных данных, если владелец разрешит).
- Редакция секретов детерминированным фильтром даёт ложные срабатывания: вырезанное значение может быть важным для классификации (например, URL с токеном) → возможен рост ложных `block`. Митигация: журнал вырезанных позиций (без значений) и разбор ложных срабатываний в пилоте.
- Абстракция бэкенда — дополнительный код в security-контуре; интерфейс обязан быть тонким (три метода, ноль бизнес-логики в реализациях).
- Предохранитель по стоимости добавляет учёт и потенциально отказы при исчерпании бюджета → деградация к существующему LLM-пути (fail-closed сохраняется).

## Reversibility

**reversible.** Смена бэкенда — конфиг; отключение периметра-расширений не предполагается (закрытый периметр — дефолт). Удаление адаптера — удаление изолированного модуля `core/src/jev/backends/`. Ключ живёт в окружении и не имеет следов в артефактах, так что «отозвать» его — одна операция вне репозитория.
