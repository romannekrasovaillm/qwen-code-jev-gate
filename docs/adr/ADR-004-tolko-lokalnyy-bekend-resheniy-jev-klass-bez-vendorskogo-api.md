# ADR-004. Только локальный бэкенд решений: Jev-класс без вендорского API

- Date: 2026-09-26
- Status: Proposed (решение A3 владельца — обязательное)

## Context

- Решение владельца (A3, 2026-09-26): **внешний TypeSafe API в целевом контуре не используется**. Причина — не цена (у вендора $0.042/MTok входных токенов, выходные бесплатны; при нашей спеке вопросов это ≈ $0.000013–0.000021 за решение, ~$4–6/мес при ежедневной работе), а приватность (в `state` уходит содержимое аргументов вызовов инструментов) и зависимость от внешнего вендора в контуре безопасности агента.
- Jev локально развернуть **нельзя**: веса закрыты, публичных весов и способа self-host нет; официально это hosted-API, «одни и те же веса обслуживают все аккаунты», вендор прямо пишет, что Jev не является drop-in заменой LLM кодинг-агента и используется **внутри** агента для решений (routing, guardrails, scoring) — то есть наша архитектурная гипотеза подтверждена, но носитель решения нужно выбирать другой.
- Существует **класс** открытых дискриминативных decision-моделей «Jev-подобного» вида: encoder-backbone + rail-голова (Laya на ModernBERT-large, 421M, Apache-2.0), causal-LM + голова на последнем токене (OpenJev/SemIf 4B и 35B на Qwen3.5), LoRA-адаптеры (Kev-0.5B на Qwen2.5-0.5B, Bespoke Nimble на Qwen3.5-9B), self-hosted drop-in с тем же API (GLiFormer 400M). Данные у них синтетические, стандартного бенчмарка категории нет, у части клонов `confidence` энтропийная, а не калиброванная.
- Протокол System One (state + вопросы `choice`/`score`/`noul` → ответы с `probabilities` и `confidence`) — открытая форма; официальный SDK принимает `baseURL` / `TYPESAFE_BASE_URL` (`TypeSafeClientConfig`), поэтому локальный сервер, реализующий ту же форму, подключается **тем же клиентским кодом**. В нашем проекте уже есть абстракция `JevBackend`, то есть смена носителя решения — вопрос конфигурации, а не переписывания гейта.
- Железо владельца: GB10 (ARM64/aarch64, unified memory), плюс x86_64-десктоп. Часть CUDA-инструментов на ARM64 требует сборки из исходников — это ограничение на выбор рантайма.

## Decision

1. **Целевой бэкенд — локальный.** Jev-стадия вызывает decision-модель по HTTP на **loopback** (`http://127.0.0.1:<port>`) или внутренний хост в контролируемом периметре. Любые вызовы внешних API из Jev-стадии запрещены (инвариант AD-10).
2. **Протокол сохраняем.** Внутренний контракт запроса/ответа остаётся формой System One: `state` + `questions{choice,score,noul}` → `answers{choice|score|noul, probabilities, confidence}`. Это даёт совместимость с официальным SDK/клиентами (при смене носителя), но **не** требует вендора: контракт — наш, сервер — наш.
3. **Кандидаты на носитель (выбор — по числам пилота, а не по обещаниям):**
   - приоритет — off-the-shelf Jev-подобные: Kev-0.5B (малая память, CPU/GPU), Laya 421M (Apache-2.0, encoder), OpenJev/SemIf 4B (Qwen3.5 + голова), self-hosted GLiFormer-реплика;
   - второй эшелон — `system-one-adapter` поверх **локальной** LLM (свой vLLM/llama.cpp);
   - третий эшелон — обучение/калибровка своей rail-головы на нашем домене (только если off-the-shelf не проходит порог приёмки).
   - `baseline_ml` (эмбеддинги + логистическая регрессия) обязателен в пилоте как дешёвый контроль: он ловит случай «decision-модель избыточна».
4. **Никакого сетевого интернета в рантайме.** Локальный сервер разворачивается рядом с агентом; отсутствие сервера — штатная деградация, а не ошибка: `unavailable` → эскалация в существующий LLM-каскад (ADR-002 §5, fail-closed без изменений).
5. **Калибровка — обязательное условие порогов.** `confidence` у клонов может быть энтропийной; до построения reliability curve/ECE на нашем курированном корпусе Jev-стадия остаётся в режимах `shadow`/`block-only` (права на автоматическое разрешение нет). Пороги — только по данным пилота и решению владельца.
6. **Ресурсная дисциплина на GB10.** Модель носителя выбирается из условия «не мешать основным нагрузкам»: приоритет малым моделям (≤4B, лучше 0.4–0.5B); перед запуском сервера — проверка занятости GPU/памяти и явное ограничение памяти процесса; правило совмещения прогонов с чужими нагрузками (стоп и вопрос владельцу) — обязательное.
7. **Эксплуатация сервиса — часть решения.** У локального сервера есть: health-проверка при старте сессии, таймаут на вызов, circuit breaker (как в ADR-002), журнал решений и версия модели/весов в записи журнала (воспроизводимость). Обновление весов — версионируемое событие, фиксируется в журнале.

## Носители по итогам разведки (2026-09-26)

Машинно проверенные факты (HF API / GitHub API / releases) сведены в `pilot/local-backends-survey.md`. Итог:

1. **Базовый носитель пилота — Ollaya + Laya** (`ollaya-dev/ollaya` v0.7.1, Apache-2.0, есть артефакт `ollaya-linux-arm64.tar.zst`; модель `convaiinnovations/laya` / ONNX-сборка `ollaya-dev/laya`, Apache-2.0). Совместимость с нашей формой достигнута «из коробки»: сервер отдаёт `/v1/systemone`, клиент настраивается через `TYPESAFE_BASE_URL=http://localhost:11435`. Заявленная калибровка (RLCD) и многоязычность — то, что нужно нашей спеке (русскоязычная страта в пилоте обязательна).
2. **Второй кандидат — Kev-4B** (`jaredpalmer/kev`, Apache-2.0, HF `jaredpalmer/kev-4b`, base Qwen3.5-4B): 4B-класс качества, калибруется temp-fit; язык `en` и больший вес в горячем пути — проверяется латентностью.
3. **Контроли пилота:** `llm_adapter` (локальная LLM на те же вопросы) и `baseline_ml` (эмбеддинги + логистическая регрессия) — обязательные по методике; `existing_llm` (текущий LLM-классификатор) — источник эталона.
4. **Исключены из целевого контура:** OpenJev (CC-BY-NC-4.0 — некоммерческая), Nimble (лицензия не определена, T=1.0 без калибровки) — см. AD-11. Возврат возможен только при смене лицензии правообладателем.
5. **Открытые риски носителя** (не снимаются до пилота): латентность arm64-бинаря без CUDA на GB10 (опубликованные 8–10 мс измерены на RTX 4090), архитектура CUDA-образа `ghcr.io/ollaya-dev/ollaya:cuda`, латентность и VRAM Kev-4B, отсутствие любых данных о переносе на русскоязычный tool-safety.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Только локальный Jev-класс (выбрано)** | Периметр закрыт, нулевая цена вызова, нет вендор-лока и ToS-рисков, работает офлайн | Качество/калибровка неизвестны (вероятно ниже Jev); нужен свой eval и калибровка; латентность и память на нашем железе — риск в горячем пути; свой сервис надо эксплуатировать; ARM64-ограничения |
| Вендорский TypeSafe API | Лучшее качество и калибровка «из коробки», минимум усилий, $0.042/MTok | Данные уходят третьей стороне; зависимость в контуре безопасности; ретенция на стороне вендора не подтверждена первоисточником; отвергнуто владельцем |
| `system-one-adapter` + локальная LLM как единственный путь | Ничего не обучать, используем готовые модели | Латентность и VRAM в горячем пути разрешений; schema-valid rate и калибровка хуже специализированных дискриминативных моделей; конкуренция за GPU |
| Своя обучаемая rail-голова сразу | Полный контроль, доменная подгонка | Долгий путь до первого результата; синтетические данные и отсутствие бенчмарка категории; риск переобучения на наш узкий домен |
| Отказ от класса (только детерминированные правила) | Просто, предсказуемо | Не обобщается на новые команды/инструменты — ровно та хрупкость, ради которой проект и затевается |

## Consequences

### Positive

- Данные (аргументы вызовов инструментов) не покидают периметр владельца — снимается главный риск внешнего вендора в контуре разрешений.
- Нулевая стоимость за решение, нет rate limits и сетевых хвостов латентности к внешнему сервису.
- Офлайн-воспроизводимость: пилот и тесты работают без интернета; веса и версия фиксируются.
- Совместимость по протоколу: тот же гейт и та же спека вопросов для любого носителя, включая возможный будущий self-host «настоящего» Jev (если веса когда-нибудь откроют — это конфигурация, не переписывание).

### Negative

- **Качество и калибровка не гарантированы**: Jev-волна молодая, данные синтетические, стандартного бенчмарка категории нет. Возможен исход «ни один открытый носитель не проходит порог» — тогда проект возвращается к `adapter`+LLM или (с новым решением владельца) к вендору.
- **Свой сервис в горячем пути**: своё развёртывание, здоровье, перезапуски, потребление памяти — новые эксплуатационные обязанности; отказ сервера = деградация к LLM-каскаду (дороже по латентности/деньгам, но безопасно).
- **Латентность на нашем железе** может не влезать в бюджет 1.2 с для крупных носителей (4B+) — ограничивает выбор моделей в сторону малых.
- **ARM64-трение**: часть рантаймов придётся собирать из исходников; это время и риск на старте.
- **Энтропийная уверенность у клонов** искажает пороги: без калибровки режим `enforce` остаётся недостижимым (это защита, но и ограничение выгоды).

## Reversibility

**reversible.** Смена носителя решения — конфигурация бэкенда за интерфейсом `JevBackend` (CMP-002); возврат к `adapter`/вендору — изменение настроек и, в случае вендора, новое решение владельца (правило AD-10 придётся менять явно — это осознанный «замок» на периметр, а не случайность). Никаких необратимых изменений в ядре нет.
