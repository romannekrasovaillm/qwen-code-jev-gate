# ADR-005. База проекта — актуальный upstream/main (форк 2.0)

- Date: 2026-09-26
- Status: Proposed (решение владельца A3 — обязательное)

## Context

- Первый прогон реализации (`hr-20260926-200537-00`) выявил расхождение уровня архитектуры: **точка врезки, объявленная в ADR-002 (`classifyAction()` в `packages/core/src/permissions/classifier.ts`), в базе ветки `arch/jev-stage1` отсутствует**. Форк стоял на `main` = `db7ec117c` (2026-03-26); там есть только `permission-manager.ts`, `rule-parser.ts`, `shell-semantics.ts`, `types.ts`. Весь AUTO-каскад (`classifier.ts`, `autoMode.ts`, `dangerousRules.ts`, `classifier-prompts/*`) — 10 554 строки в 10 файлах — появился в upstream позже.
- Причина расхождения — **ошибка архитектора в фактуре**: точка врезки определялась по свежему клону upstream (0.24.6), а не по составу самого форка. Инвариант «не выдумывай содержимое репозитория — читай инструментами» был нарушен в части *которого* репозитория смотреть.
- Харнесс отработал корректно: материализовал врезку как временный seam (`classifyAction(input, downstream)` с делегированием и fail-closed), не исказив ни один инвариант; 106 тестов зелёные, дельта — ровно два файла, fitness 27/27 после исправления ruleset.
- Решение владельца (2026-09-26, A3): **база проекта — актуальный `upstream/main`**, дельта переносится, seam заменяется настоящей врезкой. На момент решения `upstream/main` = `61e7b92b09` (2026-09-26), `classifier.ts` присутствует.
- Ограничение: старый форк (`romannekrasovaillm/qwen-code`, `main` от марта) отстал на ~6 месяцев; merge upstream в него оценён как 6211 файлов / ~2,1 млн строк diff — высокий риск, неприемлемая цена для задачи.

## Decision

1. **База ветки — `upstream/main`** (`61e7b92b09`). Рабочая ветка — `arch/jev-gate` в worktree, созданном от upstream/main. Ветка `arch/jev-stage1` (архив форка-1.0) остаётся read-only источником уже написанного кода и тестов.
2. **Перенос дельты вместо переписывания.** Код пакета `packages/core/src/jev/**` и эвиденс переносятся из `arch/jev-stage1` как есть (`git checkout arch/jev-stage1 -- …`); врезка делается **заново** — в настоящий `classifyAction()` актуальной базы (seam снимается).
3. **Стратегия форка сохраняется** (ADR-001): тонкая дельта, вся логика — в `packages/core/src/jev/**`, изменяемые upstream-файлы — `permissions/classifier.ts` и `config/config.ts`, `settings.jev.enabled=false` по умолчанию. С учётом актуальной базы к правилу добавляется обязанность **регулярной синхронизации с upstream** (форк живёт дельтами, а не разрывом).
4. **Что меняется технически по итогам Rev 2 спеки** (уже решено в §12 спеки, здесь подтверждается для новой базы): бэкенд `typesafe-api` → `system-one-http`; дефолтный endpoint — `http://127.0.0.1:11435/v1/systemone` (локальный носитель Ollaya, ADR-004); `JevSettings` включает `endpoint` и `internalHosts`; `timeoutMs` по умолчанию 3000 (эмпирика пилота-01: CPU-носитель 2.2 с).
5. **Размещение в форке.** Публикация в наш форк-репозиторий (`romannekrasovaillm/qwen-code`) допускается только как отдельная ветка/PR поверх актуального upstream-состояния; публикация дельты без синхронизации с upstream запрещена (иначе получаем второй устаревший форк).
6. **Старый worktree/ветка не удаляются** до приёмки новой базы (A4/A5) — это источник кода и точка сравнения.

## Alternatives Considered

| Вариант | Плюсы | Минусы |
|---------|-------|--------|
| **Новая ветка от upstream/main (выбрано)** | Целевой сценарий (Jev вместо stage-1 LLM) реализуем; есть LLM-baseline для сравнения и метрик; дельта изолирована и переносима; форк актуален | Перенос и перепрогон (1 цикл харнесса); надо поддерживать синхронизацию с upstream |
| Смержить upstream в старый форк | История форка сохраняется | diff 6211 файлов / ~2,1 млн строк; конфликтный merge не оценён по времени; риск недель работы ради того же результата |
| Остаться на мартовской базе | Ноль работы по переносу; дельта готова | Теряется исходная цель: в марте нет AUTO-каскада → Jev становится основным контролем, а не ускорителем; нет LLM-baseline; разрыв с upstream растёт |
| Приостановиться до выбора носителя | Не тратим прогон на перенос | Код живёт на заведомо непригодной базе; риск, что перенос всё равно понадобится позже, но уже поверх большего объёма правок |

## Consequences

### Positive

- Jev-стадия встраивается в реальный AUTO-каскад: сравнение с LLM-классификатором становится измеримым (латентность, цена, ложные блоки/пропуски) — то, ради чего проект и затевался.
- Снимается двусмысленность «seam vs врезка»: следующий прогон делает единственную врезку в существующую функцию.
- Форк уходит от полугодового отставания: дельта поверх актуального состояния, пригодная для регулярной синхронизации.

### Negative

- Цена переноса: перепрогон тестов и fitness на новой базе; возможные расхождения API между мартом и сентябрём (типы `Config`, настройки, `permission-manager`), которые придётся править по месту.
- Появляется обязанность синхронизации с upstream (без неё форк деградирует — что и произошло с форком-1.0).
- Старый форк-1.0 становится «мёртвой» ветвью: его незакоммиченные наработки владельца (`games/snake`, скрипты) остаются вне проекта — это надо развести отдельно.

## Reversibility

**reversible.** Возврат к базе форка-1.0 — переключение worktree; ветка `arch/jev-stage1` сохранена со всем кодом и эвиденсом. Перенос дельты односторонний только по времени, не по возможностям: модуль `jev/**` переносим в обе стороны.
