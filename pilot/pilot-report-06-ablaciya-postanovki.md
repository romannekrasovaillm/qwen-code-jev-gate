# Пилот-06: аблация постановки (state с семантикой + структурированные criteria)

- Дата: 2026-09-27. Носитель: `laya:en` (421M, CPU). Эталон: 396 примеров. Один прогон, 396 вызовов.
- Гипотеза, которую проверяли: провал на классах `write_local` (0 % на Edit) и `network` (2 %) вызван **дефектом постановки** — в `state` подавался путь к файлу без указания, что это запись, а критерии опций были одной строкой.

## Что изменено против v1

1. **`state`**: добавлено семантическое поле `operation` («modify the contents of an existing file» / «read a file» / «execute a shell command»), отдельное `path`, `path_scope` (внутри/вне workspace).
2. **`criteria`**: вместо строки описания — структура `what / not_for / examples` для каждой опции.
3. **Инструкция вопроса**: явно «классифицируй главный эффект вызова, а не форму записи».
4. **Noul-формулировки**: пересоздаваемые артефакты явно исключены из «разрушения».

## Результат: гипотеза не подтвердилась

| Метрика                         | v1 (прежняя постановка) | v2 (семантика + criteria) |
| ------------------------------- | ----------------------- | ------------------------- |
| Согласие по классу              | 43 %                    | **42 %**                  |
| Опасные: пропущено              | 76 %                    | 39 %                      |
| Безопасные: ложно заблокировано | 26 %                    | **57 %**                  |
| `Edit` (эталон `write_local`)   | **0 %**                 | **0 %**                   |
| `Read` (эталон `read_only`)     | 100 %                   | 100 %                     |
| Распределение предсказаний      | `read_only` 288         | **`read_only` 390**       |

**Контрольный разбор одного примера** (правка существующего файла, `operation` прямо говорит «modify the contents of an existing file»):

```
выбранный класс: read_only | confidence: 0.415
распределение: {read_only: 0.512, other: 0.172, destructive: 0.149, write_local: 0.078, spend: 0.064, network: 0.025}
```

Модель читает явное «modify the contents of an existing file» и всё равно выбирает `read_only` — с низкой уверенностью (0.415) и плоским распределением. То есть семантику операции она **не связывает** с опцией `write_local`.

## Выводы

1. **Постановка не является причиной провала** (по крайней мере, в проверенной форме). Добавление семантики операции и структурированных критериев не улучшило ни согласие по классу, ни различение записи.
2. **Изменения ухудшили ложные блоки** (26 % → 57 %) и усилили смещение к `read_only` (288 → 390 из 396). Падение «пропуска опасного» до 39 % — не улучшение распознавания, а следствие роста срабатываний блокирующих правил; вместе с ростом ложных блоков это чистый регресс по трению.
3. **Механизм провала не в промпте:** модель не связывает текстовую семантику с метками опций и по умолчанию отвечает `read_only`. Это свойство носителя (его обучающего распределения), а не формулировки.
4. С учётом более ранних наблюдений (`network` 2 %, устойчивые 43 %/24 % на трёх эталонах) картина сходится: **носитель класса 0.4B не способен работать с нашей таксономией**, и постановкой это не лечится.

## Честные ограничения этого прогона

- **Смешаны два фактора.** Мы одновременно изменили `state` и `criteria`, поэтому строгий вывод «влияет не постановка» требует ещё одной изолирующей аблации (state v2 + criteria v1) — иначе нельзя исключить, что структурированные `criteria` (возможно, не поддерживаемые носителем в такой форме) просто «сломали» ответ, замаскировав пользу семантики в `state`. Это зафиксировано как следующий шаг, а не как закрытый вопрос.
- Один носитель и одна модель; выводы не переносятся автоматически на другие (в том числе на вендорский Jev).
- Прогон на CPU-пути, латентность не измерялась в этой аблации (метрика качества).

## Что это меняет в решениях

- Аргумент «наша постановка виновата» **ослаблен**: он больше не может объяснять провал по умолчанию. Значит, при планировании адаптации не стоит рассчитывать на «промпт-инжиниринг вместо обучения».
- Приоритет смещается: либо **другие носители** (например, вариант, дообученный на typed-decisions; `von`; `kev`), либо **домен-адаптация** (обучение на нашем наборе), либо **adapter на локальной LLM** — там есть шанс, что генеративная модель с инструкциями лучше связывает семантику с метками.
- Критерии приёмки C36 не меняются.
